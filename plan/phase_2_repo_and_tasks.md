# Фаза 2: Подготовка целевого репозитория `Textualize/rich` и отбор 3 задач

> **Цель фазы:** Зафиксировать стабильную версию кодовой базы `Textualize/rich`, настроить окружение для быстрого прогона тестов и сформировать спецификации трёх разнородных инженерных задач с изолированными проверочными тестами.

---

## 1. Задачи фазы

1. **Клонирование и фиксация коммита**:
   - Клонировать `Textualize/rich` в локальный эталонный каталог (например, `C:\Experiments\benchmark_rich`).
   - Зафиксировать коммит SWE-bench Verified (чтобы кодовая база находилась в известном стабильном состоянии до внесения фиксов).
2. **Верификация тестового сьюта**:
   - Убедиться, что `pytest` выполняется внутри контейнера `pi-secure` за 5–10 секунд и все существующие тесты проходят (`PASS_TO_PASS`).
3. **Формирование 3 задач**:
   - **Задача 1**: Cross-Module Bugfix (реальный баг из SWE-bench Verified).
   - **Задача 2**: Feature Extension (функциональное расширение по архитектурным паттернам проекта).
   - **Задача 3**: ADR Compliance (задача на соблюдение зафиксированного архитектурного решения).
4. **Организация изоляции проверочных тестов**:
   - Проверочные тесты (`eval_tests/`) хранятся строго вне рабочей директории агента и подключаются харнессом только на этапе оценки результата.

---

## 2. Спецификация 3 тестовых задач

### Задача 1: Cross-Module Bugfix (SWE-bench Verified)
* **Тип:** Исправление скрытого дефекта в цепочке модулей.
* **Описание проблемы (промпт для агента):**
  > При рендеринге таблицы с вложенными элементами и включенным режимом сжатия колонок (`ratio` / `collapse`) возникает исключение `ZeroDivisionError` или некорректный перенос строк в `rich/table.py` из-за некорректного вычисления свободного пространства в `rich/_ratio.py`. Необходимо исправить расчёт пропорций без искажения ширины колонок с фиксированным размером.
* **Затронутые модули:** `rich/table.py`, `rich/_ratio.py`, `rich/layout.py`.
* **Что проверяет:** Способность агента быстро локализовать связь между табличным рендерером и вспомогательным алгоритмом распределения долей, не тратя 10–20 шагов на блуждание по всей библиотеке.
* **Проверочный тест (`eval_test_task1.py`):** Воспроизводит кейс с вложенной таблицей, проверяя корректность высоты и отсутствие исключений.

---

### Задача 2: Feature Extension (Расширение функциональности)
* **Тип:** Реализация новой фичи с соблюдением всех точек расширения.
* **Описание проблемы (промпт для агента):**
  > Требуется реализовать поддержку нового модификатора стиля `double_underline` (двойное подчёркивание в ANSI-терминалах, код `\x1b[4:2m` / `\x1b[21m`) в парсере стилей Rich, объекте `Style` и консольном экспортере HTML/SVG. Модификатор должен корректно объединяться при сложении стилей (`style1 + style2`) и поддерживаться в разметке `[double_underline]text[/]`.
* **Затронутые модули:** `rich/style.py`, `rich/default_styles.py`, `rich/_palettes.py`, `rich/terminal_theme.py`.
* **Что проверяет:** Полноту контекста. Без базы знаний средние модели часто забывают обновить либо парсер разметки, либо сериализатор стилей, либо механизм слияния.
* **Проверочный тест (`eval_test_task2.py`):** Проверяет парсинг строки разметки, рендеринг ANSI-последовательностей, сложение стилей и экспорт в HTML.

---

### Задача 3: ADR Compliance (Архитектурный инвариант)
* **Тип:** Решение задачи в строгом соответствии с принятым архитектурным соглашением (ADR).
* **Контекст в базе знаний:** В `.ki-base/adr/0002-render-protocol.md` зафиксировано:
  > Все новые визуальные компоненты обязаны реализовывать публичный генератор `__rich_console__(self, console, options) -> RenderResult` и возвращать итератор сегментов (`Segment`). Прямой доступ к внутренним буферам `console._buffer` или мутация переданных `options` строго запрещены, так как это нарушает потоковую изоляцию и вызывает гонки в `Live`.
* **Описание проблемы (промпт для агента):**
  > Разработайте компонент `Badge` (визуальная метка с закругленными границами, иконкой и текстом), который может выводиться в консоль напрямую или встраиваться в таблицы, панели и дерево. Компонент должен поддерживать динамическую подгонку под ширину родительского контейнера.
* **Что проверяет:** Обратится ли агент к ADR через `ki-manager` (или прочитает `AGENTS.md`) и выберет ли правильный контракт `__rich_console__`, либо напишет наивный класс с приватными хаками.
* **Проверочный тест (`eval_test_task3.py`):** Проверяет как визуальный результат рендеринга, так и AST-валидацию кода компонента на соблюдение инвариантов ADR (запрет доступа к `_buffer`, отсутствие сайд-эффектов в `options`).

## 3. Структура изоляции тестов (Test Harness)

Все проверочные тесты хранятся в защищённой папке харнесса:
```
C:\AI\PI\benchmark_harness\
├── eval_tests\
│   ├── test_task1_eval.py
│   ├── test_task2_eval.py
│   └── test_task3_eval.py
├── golden_patches\      # Эталонные решения для верификации тестов
└── prompts\
    ├── task1.txt
    ├── task2.txt
    └── task3.txt
```

### Процедура оценки:
1. Во время сессии агент видит только стандартный `tests/` репозитория `rich`.
2. После выхода агента из Docker харнесс:
   - Делает `git diff` для фиксации внесенных изменений.
   - Временно копирует файл `test_taskX_eval.py` в папку `tests/`.
   - Запускает: `pytest tests/test_taskX_eval.py -v`.
   - Запускает регрессионный сьют: `pytest tests/test_table.py tests/test_style.py ...`.
   - Удаляет проверочный файл и сохраняет результаты в JSON.
